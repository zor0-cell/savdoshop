# Сценарий 7-минутной демо + ответы на защите (SavdoShop)

Держи этот файл открытым в второй вкладке. Всё, что ниже, — по шаблону пособия (стр. «Seven-minute demo script»),
тайминги совпадают.

## Подготовка за 10 минут до демо
1. Двойной клик по `Запустить.bat` → открыть <http://localhost:3000> (или публичный URL, если уже задеплоено).
2. В Chrome: F12 → вкладка Console должна быть чистой.
3. pgAdmin: открой Query Tool к базе `savdoshop` (вкладки: 03_queries.sql и 04_big_data.sql).
4. Compass: подключение `mongodb://localhost:27017` → база `savdoshop` → коллекция `events`.
5. Телефон (или режим устройства F12 → 390 px) — для T1 и мобильной вёрстки.
6. Если интернет в общаге/дома плохой — включай заранее записанное видео-страховку (3 минуты).

## Поминутно

**0:00 — Проблема и идея (1 слайд).**
«За сувениром в Ташкенте надо ехать на Чарву, обходить пять рядов и торговаться, а никто не знает, есть ли товар
в наличии. SavdoShop — витрина узбекских сувениров с реальными остатками: 12 товаров, 10 клиентов, 3 заказа уже в
базе, отзывы и клики — во второй базе. Зарабатываем на комиссии 7–10% с заказа и на платном продвижении мастера.»

**0:45 — Архитектура (1 слайд).**
«Сверху браузер, четыре страницы и app.js. Они не знают про базы — только 10 маршрутов Express. Деньги и остатки в
PostgreSQL, отзывы и кликстрим в MongoDB. В облаке: Render + Supabase + Atlas. Покажу на схеме» (укажи на Figure P.2 / раздел 2 отчёта).

**1:30 — ER-диаграмма.**
«Шесть таблиц. Вот M:N: заказ ↔ товары через `order_items` с составным ключом (order_id, product_id). А вот CHECK:
`stock >= 0` и `quantity > 0` — плохие данные отбивает база, а не только код. Деньги — NUMERIC(12,2), потому что
FLOAT на 0.1 + 0.2 даст 0.30000000000000004 в цене.»

**2:15 — Живой сайт (телефон или 390 px).**
Поиск «silk» → одна карточка. Фильтр Shoes → три. Открываешь товар: цена из PostgreSQL, три отзыва из MongoDB.
«Add to cart» → корзина → форма → «Place order» → сообщение с номером заказа.
Затем F5 на странице товара: счётчик просмотров на дашборде вырос — это событие записалось в Mongo.

**3:45 — Доказательство в базе.**
pgAdmin: `SELECT * FROM orders ORDER BY order_id DESC LIMIT 3;` → новый заказ с суммой.
`SELECT * FROM order_items WHERE order_id = <номер>;` → позиции.
`SELECT * FROM payments ORDER BY payment_id DESC LIMIT 1;` → платёж.
Compass: фильтр `{ type: "purchase" }` по `events` → событие из этого же заказа.
**Провальный кейс:** закажи больше, чем остаток (например, 999 units) → «Error: Not enough stock for product N»,
и сразу покажи, что заказа в `orders` нет и `stock` не изменился — это `ROLLBACK`.

**4:45 — Big data.**
`04_big_data.sql`: 500 000 строк за одну команду. `EXPLAIN ANALYZE` без индекса → **Seq Scan, ~1110 мс**,
«Rows Removed by Filter» почти 495 000. После `CREATE INDEX idx_sales_city_date ON sales_log (city, sold_at)` →
**Bitmap Index Scan, ~82 мс**, то есть примерно **в 13 раз быстрее**.
Плюс дашборд: выручка по городам (SQL) и funnel из 50 000 событий (Mongo).
В Mongo тот же эксперимент: до индекса `{city:1, type:1}` examined 7144 при returned 887, после — examined 887, ровно столько же, сколько вернули.

**5:45 — Кусок кода, которым горжусь.**
`server/src/server.js`, маршрут `POST /api/orders`:
«Один клиент из пула, `BEGIN`, остаток проверяется не чтением, а `UPDATE ... WHERE stock >= $q RETURNING` — если
строк ноль, значит товара уже нет, я кидаю ошибку, и весь заказ откатывается. `finally { client.release() }` —
соединение возвращается в пул даже при ошибке. Два покупателя не купят последнюю штуку.»
И покажи `esc()` в `app.js`: «отзыв `<b>hi</b>` показывается текстом, а не жирным — XSS закрыт; SQL-инъекции закрыты
параметрами `$1, $2`.»

**6:30 — Дорожная карта и спасибо.**
«Дальше: регистрация и вход по bcrypt, кабинет продавца с добавлением товаров, оплата через Payme/Click, уведомления
в Telegram (заказы и так приходят по телефону). При миллионе пользователей: партиционирование `sales_log` по месяцам,
реплики для чтения, Redis для дашборда и очередь на запись событий.»

## Типовые вопросы защиты — короткие ответы
- **Зачем `order_items`?** Один заказ = много товаров. Без него пришлось бы хранить список товаров в одной колонке
  (нарушение первой нормальной формы) или создавать отдельный заказ на каждый товар.
- **Двое купили последнюю штуку?** `UPDATE products SET stock = stock - $q WHERE product_id = $id AND stock >= $q
  RETURNING stock`. Кто первый — тот получил строку; второй получает 0 строк → `ROLLBACK` и ответ 409.
- **Почему NUMERIC, а не FLOAT?** Дробные binary floating point не точны; для денег нужна точная арифметика до копейки.
- **Что ускоряет индекс и что тормозит?** Ускоряет SELECT с фильтром по (city, sold_at) в ~13 раз. Тормозит INSERT
  (каждая строка пишется и в таблицу, и в индекс) и занимает место на диске. Поэтому индексы — только на колонки из WHERE/JOIN.
- **Почему отзывы в MongoDB, а не в PostgreSQL?** Непостоянная схема: у одного отзыва есть `photos`, у другого нет;
  тегов может быть сколько угодно. Плюс отзывов и событий много и они пишутся пачками — документная база это любит.
  Деньги же требуют FOREIGN KEY и транзакций — они в PostgreSQL.
- **Как защита от SQL-инъекций?** Никакой конкатенации: только параметры `$1, $2` в `client.query(sql, [values])`.
  Плюс пользовательский текст экранируется `esc()` перед `innerHTML`, а пароли/ключи живут только в `.env`, которого нет в Git.
- **Что такое materialized view и зачем?** Это заранее посчитанный результат запроса, хранящийся как таблица:
  дашборд читает ~2900 строк вместо 500 000. Обновляется `REFRESH MATERIALIZED VIEW mv_city_daily`.
- **Как масштабируется?** Read-реплики и партиции в PostgreSQL, шардинг событий по customerId в Mongo, CDN для картинок,
  очередь на фоновые записи, разделение API на «магазин» и «аналитику».
